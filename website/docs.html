01Introduction

Postlite is a lightweight desktop HTTP client built with Tauri v2 and Rust. It covers the day-to-day request workflow: send HTTP calls, organize them into collections, reuse variables and auth, and move data in and out with Postman's open JSON formats — all in a small native window instead of a browser tab.

It is built for developers who want a fast, local API client without accounts, cloud sync, or a subscription. Everything lives in one JSON file on your machine.

Not affiliated with Postman. postlite is an independent project. "Postman" is a trademark of Postman, Inc.; the only relationship is that postlite can import and export Postman's open JSON formats.

What's inside

  • HTTP core — every standard verb plus QUERY, query params, headers, and bodies.
  • Collections & workspaces — nested folders, reordering, multiple workspaces.
  • Variables & auth — scoped interpolation and inherited authentication.
  • Automation — pre-request/test scripts and a collection runner.
  • Interop — Postman Collection v2.1, environment JSON, cURL.
  • Security — encrypted cookie jar, OS secret store, privacy masking.

02Installation

Download a build

The easiest path is a prebuilt binary or installer from the Releases page. CI builds Windows (NSIS installer preconfigured) and Ubuntu binaries and attaches them to each release.

Build from source

You need the Rust (stable) toolchain plus the Tauri v2 system prerequisites:

  • Windows — Microsoft Visual Studio C++ Build Tools and the WebView2 runtime.
  • macOS — Xcode command line tools.
  • Linux — the usual WebKit / GTK development packages.

See the Tauri prerequisites guide for details. Node.js is only needed for the verification harnesses and helper scripts — the app itself has no npm dependencies.

# install the Tauri CLI once
cargo install tauri-cli

# development with hot reload
cd src-tauri
cargo tauri dev

# production build (embeds the static UI from ../ui)
cargo build --release
# -> src-tauri/target/release/postlite(.exe)

# installer / bundle (Windows NSIS target is preconfigured)
cargo tauri build

The UI is a static folder embedded at build time. Edits to ui/ need a rebuild before they show up in the packaged app.

03Your first request

  1. Open a tab. Postlite starts with one ready. Ctrl+N opens another.
  2. Pick a method and paste a URL. Every standard verb plus QUERY is available. URL segments like :product_slug are detected as path variables and get their own table.
  3. Add details on the tabs under the URL bar — query params, headers, a body (none / raw / form-data), or auth. Query and form-data rows accept an optional description.
  4. Send with the button or Ctrl+Enter. The response panel shows status, latency, size, headers, and a pretty-printed JSON body with syntax highlighting. The body copies in one click.

Reading the response

Click any object or array line (or its caret) in the JSON view to fold it into a one-line summary with a key/item count. Collapse all / Expand all sit above the body; huge arrays start folded and children render lazily, so large responses stay fast.

Save a response as an example

The bookmark button in the response head saves any successful response as a named example — useful for documenting what an endpoint returns. The Examples picker lists them with status and date; opening one swaps the stage to the saved snapshot under a banner, with Back to live response to return. Sending again always returns to the live response.

Generate code

The Code link under Send opens a drawer that copies the request as a runnable cURL command or generates JavaScript (fetch / axios), PHP (cURL / Guzzle), Python (requests / urllib), or Go (net/http). It can also turn a pasted cURL command back into a request tab. See cURL & code generation.

04Collections & workspaces

Saving requests

Press Ctrl+S to save the active request into any collection or folder. Saved requests open from the tree into tabs; the tab strip scrolls horizontally when it overflows and keeps the active tab in view.

Organizing the tree

  • Create, rename, and delete collections and nested folders.
  • The tree is filterable and expand/collapse state is remembered.
  • Reorder by dragging any row (a grip appears on hover, a line marks the insertion point), or press Alt+Up/Down on a focused row. Order persists at every level and stays correct while the tree is filtered.
  • Rename a request by right-clicking its row (or its tab) — the new name lands in the tree and every open tab at once.

Workspaces

Create, rename, and switch workspaces from the top bar. Each workspace has its own collections, environments, and open tabs. Deleting a workspace (with confirmation) removes everything in it. Older single-workspace files migrate automatically on first launch.

05Variables & environments

Interpolation

Write {{token}} anywhere a string goes — URL, params, headers, bodies, scripts. Postlite resolves it at send time across three scopes:

ScopeWhere it's definedPrecedence
collectionThe collection's Variables tablelowest
environmentAn environment bound to the collectionmiddle
folderVariables on folders up the chainhighest

A peek overlay under the URL bar resolves each token and names the scope it came from, so you always know which value is about to be sent.

Duplicate path slashes fold in joined URLs, so {{api_url}}/api/... works whether or not the variable ends in /. The scheme and query string are left untouched.

Secret variables

Flag a variable as secret and it is masked in editors and the peek overlay. Masking is display-only — the raw value is still sent. See Privacy & masking.

Environments

Environments live in their own sidebar tab, scoped per workspace. Bind one to a collection through the selector in the top bar (next to Import); bindings persist per collection, and the bound environment participates in variable precedence.

Path variables

Segments like :product_slug in the URL get their own Path Variables table. Values are substituted URL-encoded on send and in generated code, and round-trip through Postman's url.variable format.

06Authentication

Four auth types are supported: none, Basic, Bearer, and API-key.

Auth can be set at three levels — request, folder, or collection — and inherits downward: a request with no auth of its own uses its folder's, which uses the collection's. That means one credential on the collection covers every request under it.

Credentials are masked in the Auth tab with per-row reveal. Generated code and exports always carry the real values — treat any snippet you copy as a secret.

07Request bodies

TypeBehavior
NoneNo body is sent.
RawA plain text body — JSON, XML, whatever the API expects.
Form-dataMultipart rows of two kinds: Text sends plain fields; File opens a native picker and uploads the file's bytes as a multipart part, with filename and Content-Type guessed from the extension. Empty File rows are skipped on send.

Query and form-data rows carry an optional description column (Postman's third column). Descriptions survive URL-bar edits and round-trip through Postman JSON, and file fields map to Postman's formdata type: "file" entries.

08Scripts

Every request can carry a pre-request script (runs before sending) and a test script (runs on the response). Scripts execute in a minimal sandbox that exposes a small pm API — no arbitrary Node, no file access.

ObjectWhat it gives you
pm.requestRead the outgoing request (method, url, headers, …)
pm.responseResponse code, headers, body text, json()
pm.environmentRead/write the bound environment. Writes persist, so the next request can use the value.
pm.collectionVariablesRead/write the collection's own Variables table — the value stays with that collection.
pm.variablesSession-only values; not saved.

A typical login chain — assert the response and store the token for the next request:

// Test script on a POST /login request
const body = pm.response.json();

pm.test("status ok", () => {
  pm.expect(pm.response.code).to.equal(200);
});

// Persists into the bound environment, so the next
// request can use {{token}}
pm.environment.set("token", body.data.token);

// Alternatively: stays with the collection's own table
// pm.collectionVariables.set("token", body.data.token);

Test results appear in the response's Tests tab.

09Collection runner

The runner executes a set of saved requests in order, through the exact Send pipeline — scripts, auth, environments, and cookies all apply.

  1. Right-click a collection or folder and open the runner.
  2. Pick requests in a checkbox tree. They run in the displayed order.
  3. Run. Progress is live; a Stop button halts the run. The run stops at the first failed test or transport error — a passing negative test (e.g. an expected 404) keeps it going.
  4. Inspect results per request, with test details and a body preview.

Runner results are view-only — nothing is written back to the workspace. Env chaining during a run works: a login request's script sets the token the following requests then use.

10Import & export

Postman formats

  • Import Collection v2.1 JSON — folders, requests, descriptions, path variables, file fields, auth and saved examples are carried over.
  • Export Collection v2.1 JSON that opens in Postman.
  • Import / export Environment JSON the same way.

Drag & drop

Drop files anywhere in the window. Postlite detects the content and routes it:

Dropped fileWhere it lands
Postman collection / environmentThe sidebar
postlite backupThe restore dialog
postlite settingsPreferences
cURL scriptA new request tab (a script that fails to parse opens in the cURL dialog instead)

Where exports go

Every export — collection, environment, settings, backup, code snippet — opens the native Save As dialog first. Cancelling writes nothing. The status line reports the path written.

11cURL & code generation

The Code link under Send opens a right-side drawer with three abilities:

  • Copy as cURL — a runnable command for the active request.
  • Generate code — JavaScript (fetch / axios), PHP (cURL / Guzzle), Python (requests / urllib), and Go (net/http).
  • Import cURL — paste a cURL command and get a request tab back.

Generated output carries resolved variables and inherited auth — secrets are inlined into the snippet. Handle copied code like a credential. cURL flags postlite cannot express (like -x or --compressed) are named on import rather than guessed.

12Cookies

Postlite keeps a cookie jar per workspace, on by default. Server Set-Cookie rules are respected, and a manual Cookie header always beats the jar.

  • Persistent cookies are stored encrypted (AES-256-GCM); the key lives in the OS secret store — Windows Credential Manager, macOS Keychain, or the Linux Secret Service.
  • Session cookies die when the app closes.

If no secret store is available, cookies still work for the session but nothing is saved — the Cookies drawer explains why.

Cookie Manager

The Cookies link under Send opens a drawer with rows grouped by domain, Secure / HttpOnly / SameSite chips, per-row reveal / copy / delete, domain filtering, and domain-wide delete.

Settings

Settings holds the Persist cookies switch and Clear all cookies. Turning persistence off deletes the saved jar. Deleting a workspace deletes its jar and key.

13Proxy

Three modes, configured in Settings:

  • Direct — no proxy.
  • Manual — a proxy URL plus optional username / password.
  • Environment variables — HTTP_PROXY / HTTPS_PROXY / ALL_PROXY / NO_PROXY are honored.

A bypass list sends selected hosts direct even when a proxy is active. Proxy credentials live in the OS secret store, never in settings or backups.

14Privacy & masking

Postlite masks sensitive values on screen so they don't end up in screenshots or pair-programming sessions:

  • Headers named Authorization, Cookie, or anything containing token / secret / key are masked in the request header grid, the response header table, and the Auth tab — each row has a reveal control.
  • Variables flagged secret are masked in editors and the variable peek overlay.

Masking is display-only. Everything that leaves the app — send, copy, export, generated code — carries the real values. Both masks can be switched off in Settings → Privacy.

15Settings

Open preferences with Ctrl+,. A search bar (Ctrl+F, or / while the dialog is open) filters settings live, badges each category with its match count, and jumps to the first hit. Esc clears the query before it closes the dialog.

GroupWhat you can change
AppearanceLight / dark / system theme, plus eight accent presets, each with a tuned dark and light variant
StorageAuto-save and session restore
Request defaultsTimeout, redirect policy, TLS verification, cache, response size cap
Cookies & proxyPersistence switch, clear-all, proxy mode and bypass list
Response viewDefault tab, syntax highlighting, JSON indent, word wrap
PrivacyHeader and variable masking switches
ShortcutsThe fixed keyboard shortcuts, listed for reference

Settings live in workspace.json under settings, and the whole block can be exported or imported as JSON.

17Data & backups

Collections, tabs, environments, and settings save to a single JSON file in the OS app-data directory for identifier app.postlite.desktop:

OSPath
Windows%APPDATA%\app.postlite.desktop\workspace.json
macOS~/Library/Application Support/app.postlite.desktop/workspace.json
Linux~/.local/share/app.postlite.desktop/workspace.json

The file is plain JSON: version, settings, activeWorkspaceId, and workspaces (each holding collections, environments, tabs, and the active tab). It is easy to back up or move between machines.

What stays out of the file

  • cookies/<workspaceId>.bin — the workspace's persistent cookie jar, AES-256-GCM encrypted. The random key lives in the OS secret store under app.postlite.desktop.postlite.store.
  • secrets/global.bin — the manual proxy credentials, encrypted the same way.

Backups

Import / Export in Settings writes the whole state to one .postlite.backup file and reads it back. Restore either merges beside your existing workspaces or replaces them — replace asks twice and restores the backup's preferences. Cookie jars and proxy credentials are deliberately excluded from backups.

18MCP server

Postlite ships an MCP server (mcp/server.js) that exposes your saved workspaces to AI agents — an agent can browse your collections and send requests through the same pipeline the app uses. The workspace file is read-only to the server; nothing is ever written back.

Setup

# one-time: install the three dependencies
cd mcp
npm install

# register it in your MCP client config
{
  "mcpServers": {
    "postlite": {
      "command": "node",
      "args": ["<path to repo>/mcp/server.js"]
    }
  }
}

The server reads the same workspace.json the app uses, so requests you save in Postlite are immediately visible to agents — no export step.

Tools

ToolDescription
list_workspacesWorkspaces with collection and environment counts.
list_collectionsThe folder / request tree of a workspace (id, name, method, url). Defaults to the active workspace.
get_requestA saved request by id with its folder/collection chain, effective variables (collection < environment < folder), and resolved auth.
list_environmentsEnvironments and their variables in a workspace.
send_requestSend a saved request by id, resolving variables, path variables, query params and inherited auth exactly like the app, with the app's saved HTTP settings. Accepts variable overrides applied with the highest precedence.
send_http_requestSend an ad-hoc request not saved in postlite (method, URL, headers, raw body), using the app's HTTP settings.

Two deliberate gaps when sending via MCP: pre-request/test scripts are not run, and the encrypted cookie jar is not attached — set a Cookie header manually if needed. The server returns these notes with every response.
